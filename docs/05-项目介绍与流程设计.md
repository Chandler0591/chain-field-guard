# 项目介绍与流程设计

> 本文档是项目的正式背景与流程说明,可作为开题/答辩材料的主体。
> 技术实现细节见 [docs/02-链码设计.md](02-链码设计.md),操作步骤见 [docs/03-部署手册.md](03-部署手册.md)。

## 1. 项目背景

某农产品质量安全监管项目,采用区块链技术建立检验流程管理系统,解决传统流程中
**数据易篡改、责任难追溯**的问题,确保检验数据的**真实性、完整性、不可抵赖性**。

传统检验流程的痛点:

| 痛点 | 传统做法的问题 | 区块链方案的对策 |
| :--- | :--- | :--- |
| 数据易篡改 | 检验文件存中心化数据库,后台可静默修改 | 文件存 IPFS,链上只存哈希,篡改即哈希不匹配 |
| 责任难追溯 | 操作日志可删改,"谁在何时做了什么"说不清 | 每笔操作由操作者证书私钥签名,交易永久上链 |
| 修改无痕迹 | 覆盖式更新,旧版本丢失 | 追加式修改,旧版本标记 DEPRECATED,全量可查 |
| 凭证难验证 | 纸质/图片凭证可伪造 | 数字凭证 ID 锚定链上交易,哈希比对可自证 |

## 2. 系统角色

系统涉及三个关键角色,另有监管方独立节点:

| 角色 | 组织 | 职责 | 对应链码操作 |
| :--- | :--- | :--- | :--- |
| 数据录入人 operator | Org1 | 上传基础数据、发起锚定、发起修改请求 | AnchorData / RequestModification |
| 核对人 checker | Org1 | 核对数据、二级加密签名 | CounterSign |
| 审核人 auditor | Org1 | 审批修改、终审锁定发证 | ApproveModification / FinalizeBatch |
| 监管方 regulator | Org2 | 只读监管,独立节点同步全量数据 | 仅查询(链码拒绝一切写) |

角色身份通过 X.509 证书的 `role` 属性区分,链码内强制断言;真正的权限边界在链上,不依赖前端。

## 3. 总体技术架构(开源技术)

```
浏览器(Vue3 前端,角色切换面板)
    │ HTTP /api
后端(Node.js + Express,按角色选钱包身份提交交易)
    ├─ gRPC ──► Hyperledger Fabric 2.5 联盟链(Docker:Org1/Org2 peer + Raft orderer)
    │             └─ agri-channel 上的 agrichain 链码(批次状态机 + AI 预检存证)
    ├─ HTTP ──► IPFS(Kubo,存文件本体,链上只存 CID + SHA-256)
    └─ AI 异常检测:链下规则引擎(可插拔真实模型),结论哈希上链存证
```

| 层 | 开源技术选型 |
| :--- | :--- |
| 联盟链 | Hyperledger Fabric 2.5(双组织通道 agri-channel,单节点 Raft 排序) |
| 链码 | Go 语言(批次状态机,30 测试函数覆盖流转/越权/验签) |
| 后端 | Node.js + Express + fabric-gateway(44 单测 + 15 e2e 用例) |
| 链下存储 | IPFS(kubo-rpc-client) |
| AI | 可插拔引擎(内置规则引擎 / 外部模型服务,失败自动降级;附 mock 模型服务) |
| 前端 | Vue3 + Vite + Element Plus(7 个业务页面) |

## 4. 业务流程详解

批次状态机:`INIT → ANCHORED → COUNTER_SIGNED ⇄ PENDING → FINALIZED`

```
第 1 步  数据上传与锚定(录入人)
  检验文件上传 IPFS → 得到 CID,计算 SHA-256
  → AnchorData 把 {CID, SHA-256} 写入链上(INIT → ANCHORED)
  意义:文件本体在链下,链上只存指纹,内容被篡改立即可发现

第 2 步  AI 预检(录入人,链下智能 + 链上存证)
  录入结构化检测数据(产地/农残/铅/水分/菌落总数/亚硝酸盐)
  → 链下 AI 引擎分析(可插拔:内置规则引擎 | 外部模型服务,失败自动降级)
  → 完整报告(输入/阈值/结论/引擎/模型版本/得分明细)存 IPFS
  → RecordAICheck 把 {报告CID, 报告哈希, 风险评分/等级/异常项, 模型版本} 上链
  意义:AI 结论作为独立证据锚定,不改变状态机、不覆盖任何数据;
       核对人签名前可见风险提示与各维度得分明细(红色告警=高风险),
       人工决定继续或发起修改 —— AI 辅助、不替代人工

第 3 步  二级加密签名(核对人)
  核对人从 IPFS 取回文件人工核对
  → 对数据包 batchId|CID|时间戳 做 SHA-256 + ECDSA P-256 签名
  → CounterSign 链上用核对人证书公钥验签(时间戳偏差 ≤600s 防重放)
  (ANCHORED → COUNTER_SIGNED)
  意义:签名永久上链,"核对人确认过这份数据"不可抵赖

第 4 步  修改复核(录入人/核对人发起,审核人审批)
  发现错误 → RequestModification 提交新版本 + 理由(PENDING)
  → ApproveModification 批准:新版本追加,旧版本标记 DEPRECATED(不覆盖)
  (COUNTER_SIGNED ⇄ PENDING)
  意义:基于链上操作日志的追加式修改,历史全量可审计

第 5 步  锁定与凭证(审核人)
  FinalizeBatch 锁定批次 → 拒绝一切后续写入(FINALIZED)
  → 颁发数字凭证 ID:VC-<批次号>-<交易ID>,生成二维码
  意义:数据进入只读状态,凭证 ID 可回溯到具体链上交易

第 6 步  验证与审计(消费者/监管)
  VerifyBatch:任意方拿文件重算 SHA-256 与链上比对 → MATCH / MISMATCH
  GetAllVersions:全版本历史(含 DEPRECATED)完整可见
  监管方 Org2 独立节点加入同一通道,账本自动全量同步,无需人工上报
```

**安全机制总结**:所有操作由调用者证书私钥签名(非对称加密)提交,经背书、排序后写入区块;
区块哈希链式相连,篡改任何历史记录都会破坏整条链的哈希一致性。责任追溯路径完整:
"谁(证书身份)→ 何时(区块时间)→ 做了什么(交易)→ 依据什么(AI 报告/操作日志)".

## 7. 演进方向(可答辩阐述)

1. **组织动态扩展**:联盟链支持运行时新增组织(官方 addOrg3 流程),新增监管/检测机构无需停机,
   本项目链码按证书 role 属性断言权限,新组织签发对应角色证书即可复用权限(详见
   [docs/04-网络配置原理导读.md](04-网络配置原理导读.md));
2. **AI 深化(已实现可插拔引擎)**:引擎已按 provider 模式实现——内置规则引擎(离线可用)
   与外部模型服务(AI_PROVIDER=http)可切换,模型服务不可用时自动降级回退规则引擎并
   在报告留痕;接真实异常检测模型只需实现同样的 `{ riskScore, flags, details }` HTTP 契约
   (演示可用 `node scripts/mock-ai-model.js`),结论哈希与模型版本上链留痕,监管方可追溯
   "AI 基于什么数据、用什么模型、做出什么判断";
3. **凭证生态**:数字凭证 ID 可扩展为可公开验证的链上凭证服务。
