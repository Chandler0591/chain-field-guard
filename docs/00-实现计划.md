# 链田守护 ChainField Guard Demo 实现计划

## 总体架构

- **联盟链**：Fabric 2.5，网络含 Org1（业务方：录入人/核对人/审核人三种身份）、Org2（监管方：只读身份）、Orderer（Raft）
- **链码**：Go（需先安装 Go 1.22+ 工具链），状态机 + 多版本追加
- **链下存储**：IPFS 本地 Kubo 容器（Docker），链上只存 CID + SHA-256
- **后端**：Node.js 22 + Express，`@hyperledger/fabric-gateway` 连接网关，`kubo-rpc-client` 上传 IPFS
- **前端**：Vue 3 + Vite + Element Plus（中文组件库，答辩友好）
- **角色实现**：Fabric CA 注册身份时用 attrs 标注角色（`role=operator/checker/auditor/regulator:ecert`），链码内 `AssertAttributeValue` 断言；Org2 身份在链码内被限制为只读（拒绝一切写操作）
- **开发环境**：全 WSL2 开发。代码、Go、Node、fabric-samples、git 全部位于 WSL2 Ubuntu（用户 fastrise）内，代码路径 `/home/fastrise/codes/chain-field-guard`；Windows 侧仅保留 Docker Desktop 作为容器引擎（启用 WSL 集成）和 IDE 编辑

## 批次状态机（链码核心）

```
INIT → ANCHORED → COUNTER_SIGNED ⇄ PENDING → FINALIZED
```

- `AnchorData(batchId, cid, sha256)`：录入人专用，INIT→ANCHORED，写版本 v1（ACTIVE）
- `CounterSign(batchId, signature)`：核对人专用，ANCHORED→COUNTER_SIGNED；链码用 `ClientIdentity.Verify` 以调用者证书公钥验证签名的数据包（batchId+cid+timestamp），验证通过才推进状态
- `RequestModification(batchId, newCid, newSha256, reason)`：录入人/核对人，COUNTER_SIGNED→PENDING
- `ApproveModification(batchId, approved)`：审核人专用；批准则新版本追加（currentVersion+1、ACTIVE），旧版本标记 DEPRECATED，状态回到 COUNTER_SIGNED；拒绝则请求作废、状态回到 COUNTER_SIGNED。**修改永远追加、不覆盖**
- `FinalizeBatch(batchId)`：审核人专用，→FINALIZED，生成凭证 ID `VC-{batchId}-{txId}`，此后拒绝一切写入
- `VerifyBatch(batchId, sha256)` / `GetBatch(batchId)` / `GetAllVersions(batchId)`：查询类，Org2 监管方可用，返回当前版本哈希比对结果与全版本审计历史

链上数据结构：`ProductBatch { batchId, status, versions[], currentVersion, signatures[], pendingModification, credentialId }`；`BatchVersion { version, cid, sha256, anchoredBy, anchoredAt, status(ACTIVE/DEPRECATED) }`。

## 阶段划分

### 阶段 0：环境准备（WSL2 内）

- 启动 Docker Desktop 并启用 Ubuntu 的 WSL 集成；镜像拉取代理在 Docker Desktop Settings → Resources → Proxies 配 `127.0.0.1:7897`
- 解决 WSL 内代理：首选 `.wslconfig` 启用 `networkingMode=mirrored`（WSL 2.4+，可直接访问 `127.0.0.1:7897`）；备选为 Clash 开"允许局域网连接" + WSL 内 `export http_proxy=http://<Windows主机IP>:7897`
- WSL 内安装工具链：Node 22（nvm）+ Go 1.22+
- 仓库克隆：`git clone https://github.com/Chandler0591/chain-field-guard.git ~/codes/chain-field-guard`；git 凭证桥接 Windows GCM
- 克隆 `fabric-samples`，拉取 Fabric 2.5 镜像（peer/orderer/ca 约 2GB）
- 交付物：`docs/01-环境搭建.md`

### 阶段 1：网络搭建（network/）

- 复制 fabric-samples/test-network 改造为三组织：Org1 + Org2 + Orderer
- 用 Fabric CA 注册 4 个身份：operator/checker/auditor（Org1）、regulator（Org2），带 role attrs
- 创建通道 `agri-channel`，部署一个 Hello 链码验证环境连通性
- 交付物：`network/` 全套配置 + `network/scripts/start.sh`、`createChannel.sh`、`deployCC.sh`（生成密钥材料不入库，`.gitignore` 已覆盖）

### 阶段 2：链码开发（chaincode/agrichain/，核心）

- 实现上述状态机全部 9 个函数 + 角色断言 + 链上签名验证（`ClientIdentity.Verify`）
- 用 contractapi mock stub 写单元测试覆盖状态流转与越权断言
- 部署到 `agri-channel`（Org1 部署，Org2 查询）
- 交付物：链码源码 + 测试 + `docs/02-链码设计.md`（状态转换图、函数签名表）

### 阶段 3：后端 API（backend/）

- Express + `@hyperledger/fabric-gateway`，钱包按角色切换身份提交交易（前端角色切换 → 后端选对应 wallet）
- 路由：`POST /api/upload`（IPFS+SHA256）、`POST /api/batches`、`POST /api/batches/:id/countersign`、`POST /api/batches/:id/modification-request`、`POST /api/batches/:id/modification-approve`、`POST /api/batches/:id/finalize`、`GET /api/batches/:id`、`GET /api/batches/:id/versions`、`POST /api/verify/:id`
- 签名模块：核对人私钥（node:crypto ECDSA P-256）对数据包摘要签名，签名随交易上链、链上验证
- 交付物：backend 源码 + 身份注册脚本 + `.env.example`

### 阶段 4：前端（frontend/）

- 页面：角色切换面板、上传锚定页、核对签名页（含 IPFS 文件预览）、修改复核页、锁定与凭证页（展示凭证 ID，可生成二维码）、消费者验证页、监管审计页（全版本历史表格）
- 交付物：frontend 源码（Vite 构建，`npm run dev` 即可联调）

### 阶段 5：串联演示与文档

- 端到端跑通：录入人上传 → 核对人签名 → 录入人发起修改 → 审核人批准 → 审核人锁定 → 消费者输入批次 ID 验证 → 监管方查全量历史
- 用 tape 或简单脚本做一次压测数据（可选，答辩加分）
- 完善 README、`docs/03-部署手册.md`（从零部署到演示的完整步骤）

## 关键风险与对策

1. **代理链路（最大坑）**：WSL 内访问外网需先打通代理（mirrored 模式或 http_proxy + Clash 开 LAN）；Docker Desktop 镜像拉取另需在 GUI 配代理；两者缺一都会卡在阶段 0。所有 Fabric 镜像（peer/orderer/ca）约 2GB，提前拉取
2. **三组织改造复杂度**：若阶段 1 遇阻，降级为先跑官方双组织 test-network，Org2 只读约束用链码内 MSPID 断言兜底，不影响业务演示
3. **链上签名验证**：签名数据包必须在链码内可重现（batchId+cid+timestamp 拼接规则前后端约定一致），timestamp 用链码侧 `stub.GetTxTimestamp()`
4. **版本追加一致性**：所有写操作只 append 不 update，审计查询走 versions 数组而非覆盖字段
