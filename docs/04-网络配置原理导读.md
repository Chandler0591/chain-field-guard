# 网络配置原理导读 —— 从 test-network 到联盟治理

> 定位:补"三阶段学习路线"中阶段 2(改造开源项目学习 crypto-config/configtx)的知识缺口。
> 本项目没有从零手写网络配置,而是以官方 test-network 为底座(阶段 1 的成果)。本篇以本项目
> `network/` 为**实物教材**,讲透 Fabric 网络配置原理,并回答一个核心问题:**联盟链的组织能否扩展、怎么扩展、扩展后链码权限要不要改**。
> 读完可以对着 `network/configtx/configtx.yaml`、`network/addOrg3/`、`network/organizations/` 逐段指认。

## 1. Fabric 网络配置全景图

一个 Fabric 网络的诞生,按时间顺序经过四个环节:

```
① 证书与 MSP         ② 通道配置 configtx         ③ 创世区块/配置更新         ④ 链码生命周期
(每个组织的"身份证") → (联盟的"宪法") → (宪法生效) → (业务规则上链)
```

| 环节 | 回答什么问题 | 本项目落点 |
| :--- | :--- | :--- |
| ① 证书与 MSP | "我是谁、属于哪个组织、能干什么" | `network/organizations/`(CA 签发 + 角色属性) |
| ② 通道配置 | "联盟里有哪些组织、决策规则是什么" | `network/configtx/configtx.yaml` |
| ③ 创世区块 | "网络启动时宪法如何生效;运行中如何修宪" | `network.sh up` 生成;`addOrg3/` 演示动态修宪 |
| ④ 链码 | "业务函数谁可以调用、状态怎么流转" | `chaincode/agrichain/`(角色断言) |

**核心结论(Fabric 与其他链的本质区别)**:组织的本质是**一套 MSP(证书体系)**,不是一台服务器。
一个组织可以只挂一个 peer 节点(本项目),也可以挂十个;组织的数量和名称由**联盟治理规则**决定,
而不是技术限制。Org1、Org2 只是 Demo 阶段的简化编号,生产环境完全可以命名为"XX 农业局""XX 检测中心"。

## 2. 组织 = MSP:一套"身份证"体系

### 2.1 MSP 是什么

MSP(Membership Service Provider)定义了一个组织的信任根:包含根证书、中间证书,以及"什么样的证书
算本组织成员"的规则。peer 节点验签时,用 MSP 判断"这个签名是否出自 Org1"。

### 2.2 角色 ≠ 组织(本项目设计关键)

本项目 4 个业务角色,**不是** 4 个组织,而是"2 个组织 + 证书属性":

| 角色 | 组织 | 区分方式 | 注册命令(registerEnroll.sh) |
| :--- | :--- | :--- | :--- |
| operator 录入人 | Org1 | 证书 role 属性 | `--id.attrs '"role=operator:ecert"'` |
| checker 核对人 | Org1 | 证书 role 属性 | `--id.attrs '"role=checker:ecert"'` |
| auditor 审核人 | Org1 | 证书 role 属性 | `--id.attrs '"role=auditor:ecert"'` |
| regulator 监管 | Org2 | 证书 role 属性 | `--id.attrs '"role=regulator:ecert"'` |

- 角色属性在 CA 注册时写入证书(`ecert` 表示写进证书而非临时属性),链码用
  `ClientIdentity.AssertAttributeValue("role", "operator")` 断言;
- 这种设计的收益后面第 5 节会展开:**新增组织时链码权限几乎不用改**。

### 2.3 顺便理解 NodeOUs

`EnableNodeOUs: true` 时,证书按 OU 区分 `admin / peer / client / orderer` 四类身份
(见 `configtx.yaml` 中 Org1 的 `Policies` 引用了 `Org1MSP.admin / .peer / .client`)。
"组织管理员"和"组织普通成员"由此区分——第 4 节的多数派投票,投的就是"各组织 Admin"的签名。

## 3. configtx.yaml 逐段导读(对照本项目实物)

打开 `network/configtx/configtx.yaml`,从上到下四个关键段:

### 3.1 Organizations 段 —— 联盟成员名单

```yaml
Organizations:
  - &OrdererOrg        # 排序组织(网络基础设施)
    ID: OrdererMSP
    MSPDir: ../organizations/ordererOrganizations/example.com/msp
    Policies:          # 本组织的 Readers/Writers/Admins 由哪些证书充当
      Admins: { Type: Signature, Rule: "OR('OrdererMSP.admin')" }
  - &Org1              # 业务方(本项目:录入/核对/审核)
    ID: Org1MSP
    MSPDir: ../organizations/peerOrganizations/org1.example.com/msp
  - &Org2              # 监管方(本项目:只读)
    ID: Org2MSP
    MSPDir: ../organizations/peerOrganizations/org2.example.com/msp
```

要点:**在这里加一个组织定义,不等于它加入了通道**——还要看 Application 段是否把它列入
通道参与者名单。这就是第 4 节两种扩展方式的差别所在。

### 3.2 Capabilities 段 —— 版本一致性开关

```yaml
Capabilities:
  Channel:   { V2_0: true }
  Orderer:   { V2_0: true }
  Application:{ V2_5: true }
```

Capability 是"全网最低功能版本"的强制开关:声明 `V2_5: true` 后,不支持 V2.5 特性的旧节点
会**拒绝参与**,防止不同版本节点算出不同的世界状态。部署手册排查表中的
`system-channel ... requires unsupported orderer` 报错,根源就是镜像版本与这里声明的
能力版本不匹配(旧镜像 1.4.x 读不懂 2.x 的通道配置)。

### 3.3 Application 段 —— 联盟决策规则(重点)

```yaml
Application: &ApplicationDefaults
  Policies:
    Admins:    { Type: ImplicitMeta, Rule: "MAJORITY Admins" }
    LifecycleEndorsement: { Type: ImplicitMeta, Rule: "MAJORITY Endorsement" }
    Endorsement: { Type: ImplicitMeta, Rule: "MAJORITY Endorsement" }
```

`ImplicitMeta` 是"递归取各组织同类策略"的聚合规则:

- `MAJORITY Admins`:修改通道配置(比如**新增组织**)、升级链码定义,需要**超过半数组织的 Admin 签名**;
- `MAJORITY Endorsement`:链码背书与生命周期按多数派背书策略走。

这正是"联盟治理"的制度根源:**新增一个组织不是技术员改个文件,而是一次联盟投票**。
本项目只有 Org1、Org2 两个应用组织,MAJORITY(>1)意味着两者都必须同意。

### 3.4 Orderer 段 —— 共识与区块

本项目排序服务为单节点 Raft(`etcdraft`)。Fabric 的排序服务只负责**定序 + 打包区块**,
不执行链码;执行与校验由各组织 peer 完成。单节点 Raft 适合 Demo,生产至少 3 节点才有容错。

## 4. 组织扩展的两种方式(核心)

### 方式一:创世配置预定义(简单,但不灵活)

在 `configtx.yaml` 的 Organizations 与 Application.Organizations 中**预先写好** Org3、Org4,
启动网络时就全部创建好。适合"组织数量确定且固定"的场景。

**缺点**:组织的变更写进了创世区块,运行后想再加组织,**必须重建网络**(数据全部作废重来)。
对本项目的业务场景(监管机构、检测机构可能陆续加入),这种方式不合适。

### 方式二:通道配置更新动态新增(推荐,联盟链标准做法)

Fabric 支持**网络运行过程中**通过通道配置更新(Channel Configuration Update)新增组织,
流程如下:

```
① 新组织生成自己的 MSP 证书(自有 CA 或托管 CA)
② 现有成员把新组织的 MSP 信息组装成"配置更新交易"
③ 现有成员按通道策略签名投票,达到多数派后提交
④ 新组织的 peer 启动并加入通道,开始同步账本
```

**全程不需要重启网络,其他组织不停机**。这是联盟链治理灵活性的直接体现。

### 4.1 本项目的现成示例:addOrg3/

官方 test-network 自带完整示例,`network/addOrg3/` 目录已随仓库提供,一条命令即可体验:

```bash
cd network
./network.sh up createChannel -ca        # 已启动网络则跳过本行

cd addOrg3
./addOrg3.sh up -c agri-channel          # 注意:本项目通道名是 agri-channel(脚本默认 mychannel)
```

`addOrg3.sh` 内部依次做了上面四步:

1. 按 `org3-crypto.yaml` 用 fabric-ca 生成 Org3MSP 证书(`organizations/peerOrganizations/org3.example.com/`);
2. 启动 Org3 的 peer 容器;
3. 组装并签名"把 Org3MSP 加入 agri-channel 应用组织列表"的配置更新交易(需 Org1、Org2 各出一个签名);
4. 提交更新,Org3 的 peer 加入通道、拉取账本。

**期望结果**:`docker ps` 新增 `peer0.org3.example.com` 容器;日志出现 Org3 加入 agri-channel 的提示。
在 Org3 的 peer 上执行 `peer channel list` 可见 `agri-channel`,且能同步查询到此前所有批次(账本完整复制)。

## 5. 新增组织后,链码权限怎么调

### 5.1 通用做法:按 MSPID 硬编码 —— 加组织就要升级链码

若链码这样写(JS 伪代码):

```javascript
if (ctx.clientIdentity.getMSPID() !== 'Org1MSP') {
    throw new Error('只有 Org1 可以调用 AnchorData');
}
```

新增 Org3 后想让 Org3 也能锚定,就必须**升级链码**,把判断改成:

```javascript
const allowedMSPs = ['Org1MSP', 'Org3MSP'];
if (!allowedMSPs.includes(ctx.clientIdentity.getMSPID())) {
    throw new Error('无权限调用 AnchorData');
}
```

Fabric 链码支持版本化升级(升级同样需要多数派审批),旧版本调用记录仍在链上可追溯——
可行,但"加一个组织就升级一次链码"的治理成本会随联盟扩大而上升。

### 5.2 本项目的做法:按证书 role 属性断言 —— 组织可扩展,权限可复用

本项目链码断言的是**角色属性**而非组织 ID(`access.go`):

```go
// 要求调用者证书携带 role=operator 属性(任何组织签发的均可)
func requireRole(ctx contractapi.TransactionContextInterface, role string) error { ... }

// 组织级防线:Org2(监管)默认只读,一切写函数开头先过这一关
func rejectRegulatorWrite(ctx contractapi.TransactionContextInterface) error { ... }
```

由此得到两个直接收益:

| 场景 | 是否需要改链码 | 说明 |
| :--- | :--- | :--- |
| 新组织(如第三方检测机构)要以"录入人"身份调用 | **不用改** | 新组织给自己成员签发带 `role=operator` 的证书即可,链码只认 role 属性,不认组织 ID |
| 新组织希望默认只读(如新增监管机构) | 一次小升级 | 把新 MSPID 加入 `rejectRegulatorWrite` 的拒绝名单,其余逻辑不动 |
| 希望"某组织的某角色才有某权限"的组合规则 | 需按需扩展 | 可参照 `requireRole` 增加组织维度判断,属功能增强而非推倒重来 |

**更进一步的思路(生产可考虑)**:把权限规则从硬编码改成**链上可配置状态**——链上存一张
"角色 → 允许函数"映射表,新增组织时调用一次 `UpdatePermission` 写入配置即可,连链码升级都省了。
本项目 Demo 阶段用 role 属性方案已足够,`UpdatePermission` 可作为答辩时"演进方向"阐述。

### 5.3 两种做法对比

| 维度 | MSPID 硬编码 | 本项目 role 属性方案 |
| :--- | :--- | :--- |
| 新增同职能组织 | 升级链码 + 联盟审批 | 签发带 role 证书即可 |
| 权限粒度 | 组织级 | 角色级(更细) |
| 治理成本 | 随组织数线性上升 | 基本不变 |
| 实现复杂度 | 低 | 略高(注册时带属性) |

## 6. 组织映射:Demo 现状 vs 生产建议

### 6.1 Demo 现状(以本项目代码为准)

| 组织 | 承担角色 | 说明 |
| :--- | :--- | :--- |
| Org1MSP | operator 录入 + checker 核对 + auditor 审核 | 三个身份靠证书 role 属性区分,写入同一组织 |
| Org2MSP | regulator 监管 | 链码内 `rejectRegulatorWrite` 限制为只读 |

### 6.2 生产环境扩展建议(按业务职能拆分组织)

| 组织编号 | 业务角色 | 说明 |
| :--- | :--- | :--- |
| Org1 | 数据录入方 | 负责农产品基础数据和检测报告录入 |
| Org2 | 核对方 | 负责数据准确性核对和二级签名 |
| Org3 | 审核方 | 负责修改审批和终审锁定 |
| Org4 | 监管方 | 只读节点,独立同步全量数据 |
| Org5(可选) | 消费者协会/第三方检测机构 | 独立验证节点 |

- Demo 的"一组织多角色"靠证书属性区分,生产建议的"一组织一职能"靠治理结构区分——**两种模式链码核心逻辑都不用改**;
- 拆分组织时,现有 4 个身份可平移到新组织:例如把 auditor 的注册从 ca-org1 迁到 Org3 的 CA(注册命令不变,只换 CA 与 MSP 路径),链码 `requireRole("auditor")` 继续生效。

## 7. 答辩话术(可直接引用)

> "联盟链支持组织动态扩展:新增监管节点或第三方检测机构时,通过通道配置更新即可完成,
> 无需停机重建网络;本项目的链码按证书角色属性做权限断言,新组织签发对应角色证书即可
> 复用权限,权限规则无需随组织增加而频繁升级。这是联盟链区别于私有链的重要优势,
> 也是本系统适配多角色监管场景、具备可落地性的基础。"

## 8. 动手练习(可选,约 30 分钟)

1. **跑一遍动态加组织**:执行 4.1 的 `addOrg3.sh up -c agri-channel`,观察 peer0.org3 容器出现、账本同步;
2. **验证权限复用**:参考 `network/organizations/fabric-ca/registerEnroll.sh` 中 operator 的注册命令,
   在 Org3 的 CA 上注册一个带 `role=operator` 的用户并签发证书,用该身份调用后端
   `POST /api/batches` 锚定一个批次——成功即证明"组织可扩展、权限可复用";
3. **验证只读防线**:给该用户签发 `role=regulator` 证书,再次尝试锚定——应被链码拒绝
   (注意:Org3MSP 不在 `rejectRegulatorWrite` 名单中时,role=regulator 本身不能调用写函数,
   因为写函数都有 `requireRole(operator/checker/auditor)` 断言;把 Org3MSP 加入拒绝名单后,
   连查询外的任何写调用都会在入口被拦截)。
